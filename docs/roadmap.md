# Roadmap — from scaffold to space flight

Where the project stands and what stands between here and rendered 3D flight.
Phases 0–4 (media, PE analysis, function discovery, codegen) are done; this
document covers 5 onward. Each phase lists its exit criterion — the thing that
must be observably true before the next phase is worth starting.

## Phase 5 — Compile and link  ✅

**Exit criterion:** `xvt_recomp.exe` builds and runs recompiled guest code.

Done in this session. What it took:

| Piece | Notes |
|-------|-------|
| `CMakeLists.txt` | MSVC x86, `/BASE:0x10000000` so the guest's 0x400000–0xB60000 stays free, `/DYNAMICBASE:NO`, no `/GL` (it misoptimises the global register model) |
| `src/game/recomp/recomp_types.h` | Copied from XWA unchanged — the register/memory/dispatch model is target-independent |
| `src/game/imports.c` | Generated by `tools/gen_bridges.py` from `config/pe_analysis.json`: 188 bridges, 182 live, 6 DirectX creates left as stubs for Phase 7 |
| `src/game/main.c` | Written fresh for XvT: memory map, dispatch lookups, native registry, VEH handler. No per-function overrides yet |

Four toolchain bugs were fixed rather than worked around in the output:

1. **`loop` was not a block leader** (`disasm.py`) — `loop`'s branch target never
   became a basic-block start, so the lifted `goto` had no label. Added
   `loop`/`loope`/`loopne` to `COND_JUMPS`.
2. **`int3`-only blocks emitted a label with no statement** (`lifter.py`) — C
   requires a statement after a label. Now emits a null statement.
3. **Call targets were never fed back into discovery** (`disasm.py`) — the linear
   `E8` scan skips 5 bytes per hit, so a call preceded by a stray `0xE8` byte was
   missed and the callee never lifted (2 link errors). Discovery now iterates to
   closure over each function's own call targets.
4. **Shifts did not set flag state** (`lifter.py`) — **the important one.** A
   `jcc` after `shr`/`shl`/`sar` matched the *previous* flag-setter instead. In
   the guest `memset` (`sub_004FECE0`) this turned `shr ecx,2 / je` into a test of
   an unrelated `and edx,3`, sending a 64 KB fill down the byte-remainder path
   with `edx = 0` — a 4-billion-iteration write that ran off the end of the
   committed heap on the first frame of CRT startup. Shifts now register a
   result-vs-zero flag state.

Audited the rest of that bug class afterwards: `adc`, `sbb`, `shld`, `shrd`,
`rol`, `ror`, `mul`, `imul` also set flags without registering flag state. All 9
sites in this binary where one is followed by a conditional turned out to have an
intervening `cmp`, so none is currently mis-lifted — left alone rather than fixed
speculatively. `sahf` is deliberately not registered: it follows `fnstsw` and the
FPU compare state set earlier is the correct source.

The memory layout differs from XWA's and is worth recording: XvT's original low
addresses (0x100000–0x400000) hold *this* process's mapped sections, so the guest
stack cannot live there. It is allocated wherever the OS offers (identity mapping
makes any host address a valid guest stack address); only the image range
0x400000–0xB60000 is pinned, committed inside the default heap's existing
reservation.

## Phase 6 — Boot to WinMain  ✅

**Exit criterion:** the game's own `WinMain` runs and reaches window creation.

Reached in the same session, and it came almost free — **XvT's guest CRT startup
runs to completion unmodified.** This is the sharpest divergence from XWA so far:
XWA had to bypass its VC6 CRT startup entirely (it crashed in locale/env init)
and hand-initialise `__sbh_threshold`, the CRT lock table, the heap handle and
`_pctype` before calling `WinMain` directly. XvT's VC4.x CRT needs *none* of
that — `sub_004FD970` runs heap init, locale init (`GetLocaleInfoA/W`,
`IsValidCodePage`, `IsValidLocale`, `GetUserDefaultLCID`), and enters `WinMain`
on its own. The older, simpler CRT is genuinely easier to recompile.

So `XVT_ENTRY` stays at the PE entry point, `g_manual_overrides[]` stays empty,
and none of XWA's CRT-global patches were needed. Two things were required:

1. **Native WndProc bridge.** Windows calls the window procedure directly, and
   the guest's procedure has no executable code at its VA. Rather than XWA's
   approach (patch the 4-byte immediate at a known instruction address), the
   `RegisterClassA` bridge swaps `WNDCLASSA.lpfnWndProc` for one of four native
   trampolines that re-enter the guest through the dispatch table, saving and
   restoring the whole register model (Windows can call it re-entrantly, e.g.
   during `CreateWindowExA`). Target-independent, and it needs no knowledge of
   any instruction address.
2. **`GetProcAddress` native registration.** The bridge now registers the raw
   DLL address it returns, with its arg count, so the later indirect call
   through that address can be bridged. First user: `IsProcessorFeaturePresent`.

One function had to be lifted by hand: the WndProc `sub_004C81E0` is referenced
only as *data* (a `WNDCLASS` field), never called, so neither the call-target
scan nor the closure pass found it. `tools/lift_extra.py` covers this case for
now. If more turn up, the general fix is to mine `.reloc` — XvT has a relocation
table, so every absolute address embedded in code or data is enumerable, and any
that lands in `.text` is a code pointer. That is precise, cheap, and unavailable
in XWA (fixed base, no `.reloc`) — worth doing here once it earns its keep.

Runtime state at the end of the phase: 2,924 recompiled calls, 1,114 indirect
calls, window created, real Windows messages dispatched into guest code, stopping
cleanly at `DirectDrawCreate`.

## Phase 7 — Win32/DirectX HAL

**Exit criterion:** a window appears and the game's main loop runs.

1. **Native WndProc bridge.** Windows cannot call into our lifted code, so the
   `lpfnWndProc` immediate in the guest's `RegisterClassA` setup is patched to a
   native bridge that re-enters guest code through the dispatch table.
2. **COM mocks** (`com_mocks.c`) for DirectDraw / Direct3D / DirectInput /
   DirectSound / DirectPlay, hung off the `0xBBxxxxxx` vtable markers. XWA's
   2,700-line implementation is the reference, **but its vtable layouts are the
   wrong version** — this was checked rather than assumed, and the answer is
   decisive. Reading the call sites in `sub_004C8AE0` (the DirectDraw init):

   | vtable offset | slot | Method | Args (+`this`) |
   |---|---|---|---|
   | `+0x50` | 20 | `SetCooperativeLevel(hwnd, 0x51)` | 2 |
   | `+0x54` | 21 | `SetDisplayMode(0x280, 0x1E0, bpp)` | **3** |
   | `+0x18` | 6 | `CreateSurface(desc, ppSurf, NULL)` | 3 |
   | `+0x58` | 22 | `WaitForVerticalBlank(...)` | 2 |
   | `+0x30` | 12 | `GetDisplayMode(desc)` | — |
   | `+0x7C` | 31 | `SetPalette(...)` — on a *surface*, not the DD object | 1 |

   `SetDisplayMode` taking **three** arguments (640×480×bpp) settles it: this is
   **`IDirectDraw` v1**, not `IDirectDraw2` (5 args) and certainly not XWA's
   `IDirectDraw4`. Slot 31 on a surface is `IDirectDrawSurface::SetPalette`.
   The mode is 640×480 fullscreen-exclusive (`0x51` =
   `DDSCL_EXCLUSIVE|DDSCL_FULLSCREEN|DDSCL_ALLOWREBOOT`), 8-bit palettised, with
   the `DDSURFACEDESC` staged around `0xA49576`–`0xA4957E`.

   So: build the DirectDraw mock to the v1 layout, and treat XWA's file as a
   source of *method bodies*, not of slot indices.
3. Wire the 6 stub bridges (`DirectDrawCreate`, `DirectInputCreateA`,
   `DirectSoundCreate`, DPLAYX ordinals 1/2/4) to the mock creates. This is where
   the run currently stops: `DirectDrawCreate` returns nothing, and
   `sub_004C8AE0+0x204D` dereferences the NULL interface pointer.

## Phase 8 — 2D presentation

**Exit criterion:** the menus/frontend are visible and respond to input.

1. Present the guest's DirectDraw primary surface into a real window. Start with
   `StretchDIBits` — XvT is 8-bit palettised, so this is a palette lookup plus a
   blit, and it is enough to see the frontend. A D3D11 backend is a later
   optimisation, not a prerequisite.
2. Palette handling: `IDirectDrawPalette::SetEntries` feeds the DIB colour table.
3. Input: DirectInput device mocks feeding real keyboard/mouse state.

This is the phase that proves the whole stack — if the frontend renders, the
software rasteriser's output path works, and flight is the same path with
different content.

## Phase 9 — Flight

**Exit criterion:** rendered 3D space flight.

The prior sessions' static analysis already mapped the route (`docs/directplay.md`,
`docs/singleplayer-spawn.md`), and its central finding shapes this phase:
**XvT's single-player craft spawn is local — no DirectPlay involved.**

1. Mission select → `.tie` load (`sub_00455B80` chain, filename buffer `0x517108`).
2. Craft activation: `sub_00409390`, driven from `0x004DC947`. Per-craft field
   recipe already extracted — FG descriptor stride `0x23`, object record stride
   `0xEC` at `fg+0x1F`, active tag `fg+0x1A = 2`, render status `obj+0x2CA ∈ {2,4}`.
3. Software rasteriser writes the DirectDraw back buffer; Phase 8's present path
   carries it to the screen unchanged.

DirectPlay only needs to work for multiplayer, which is out of scope for
first flight.

## Phase 10 — Cross-validation report

**Exit criterion:** a written finding fed back to the XWA effort.

The reason this repo exists. Two deliverables:

1. **Toolchain generality** — already demonstrated: the unmodified XWA pipeline
   lifted a second Totally Games title. The four bugs fixed in Phase 5 are
   *general* lifter bugs that XWA's output also contains (particularly the shift
   flag bug) — XWA should be regenerated with the fixed toolchain and retested.
   This is the first concrete payoff and it flows XvT → XWA, as intended.
2. **The spawn recipe** — if XvT reaches flight through its local spawn path,
   that confirms the hypothesis that XWA's black flight view is the DirectPlay
   loopback being the wrong route, and the per-craft field set from
   `sub_00409390` maps onto XWA's local builder `sub_0041EF60`.

## Known issues, queued

**1. The x87 stack is per-function and must be global.** Generated code declares
`double _st[8] = {0}` inside every function, so a guest function that returns a
value in `st(0)` returns a zeroed local copy to its caller. XWA hit this and has
already fixed it — `recomp_types.h` there now declares `extern double _st[8]`
and `extern int _fp_top` — after tracing it to the CRT `__ftol` helper returning
0 for *every* float→int conversion. XvT has not been bitten yet because nothing
before the DirectDraw wall depends on an FPU return value, but flight math will
hit it immediately.

The fix is two-part and should be done before Phase 9: move `_st`/`_fp_top` to
globals in `recomp_types.h` + `main.c`, and stop `lifter.py` emitting the local
declarations in each function prologue. That means a full regen (~35 min), so it
is worth batching with any other lifter change. **Do this first next session** —
debugging flight math on a broken FPU return path would waste a lot of time.

**2. Data-referenced functions are not discovered.** `sub_004C81E0` (the WndProc)
is referenced only as a `WNDCLASS` field, so neither the call-target scan nor the
closure pass finds it; it is lifted by hand via `tools/lift_extra.py`. If more
turn up, mine `.reloc` (XvT has a relocation table — every absolute address
embedded in code or data is enumerable, and any landing in `.text` is a code
pointer). Precise, cheap, and not available in XWA, which has no `.reloc`.
